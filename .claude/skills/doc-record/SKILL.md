# doc-record · 把重要内容沉淀进 docs/

> **何时用**：仅当用户**明确要求**把内容记录/沉淀进文档时——例如输入 `/doc-record`（支持斜杠命令的环境），或在 Claude Desktop 等无斜杠 UI 的环境里用自然语言说「doc-record 一下」「把刚才的结论记进 docs」「归档到文档」。**除此之外不要自动触发**（不要因为对话里出现"重要结论"就主动调用；尤其不要把"note/记一下"这类日常口语误当触发信号——只有明确指向"写进文档"时才执行）。
>
> **职责边界（务必区分，不要混淆）**：
> - `docs/` = **面向人**（使用者 / 维护者，不一定懂代码）：怎么用、为什么这样、有什么坑、改动时要注意什么。**用自然语言讲清"是什么 / 为什么 / 怎么做 / 注意什么"。**
> - `ARCHITECTURE.md` = 面向 AI 的代码地图（文件职责 / 函数位置 / 数据流）。**本 skill 不写它**（那是 AGENTS.md §1 的职责，由代码改动驱动）。
> - 若用户要记的是"代码结构变化" → 提醒应更新 `ARCHITECTURE.md`，而不是塞进 docs/。

## 输入

- `$ARGUMENTS`：用户在 `/doc-record` 后跟的说明（可空）。
  - **有说明**：以它为本次要沉淀的主题/要点。
  - **为空**：回顾当前对话，自己提炼出"值得长期留存、对使用者/维护者有价值"的结论作为候选，**先列给用户确认**再落盘。

## 执行步骤

### 1. 确定要沉淀什么（先想清楚，再动笔）

从当前对话里筛出**真正值得长期留存**的内容，典型类别：

- **重要逻辑点**：某功能实际是怎么运作的（尤其与直觉/旧理解不同的地方）。
- **注意事项 / 坑**：什么情况下会出问题、有什么前置条件、什么参数组合有副作用。
- **使用备忘**：正确的操作步骤、推荐做法、命令示例。
- **设计取舍 / 现状声明**：当前实现的边界（"X 暂时等同 Y"、"Z 仅 Python API 未接 CLI"这类**诚实的现状**）。
- **决策记录**：为什么这么定，避免以后反复纠结或推翻。

**不要沉淀**：一次性的调试过程、临时状态(那是 HANDOFF.md)、未完结的活、无长期价值的闲聊。

> 诚实第一：只写**已确认为真**的内容。拿不准的标注"待核实"，不要把猜测写成结论。

### 2. 选择落盘位置（先复用，不滥建新文件）

先看 `docs/` 现有文件（命名惯例 `NN-主题.md`，如 `01-技术栈说明.md` / `02-使用说明.md`）：

- **能归入已有主题** → 追加/更新到对应文件的合适小节（优先）。使用/维护/调试类的零散备忘（踩坑、注意事项、自查命令）优先并入 `docs/02-使用说明.md` 对应小节（部署 / 维护 / 调试三块）。
- **确实是一个全新的大主题**（内容足够成体系）→ 才新建 `docs/NN-主题.md`（NN 取下一个序号），并在文件顶部加一句用途说明 + 配套文档引用，并同步更新 `docs/00-目录.md`。

不确定归到哪时，**先问用户**一句"归到 X 还是放进 02-使用说明?"。

### 3. 写入（保持可读、可检索、不重复）

- 用**中文**、自然语言，面向"不一定懂代码的维护者"，必要处给命令/路径/示例。
- 结构化：用小标题、表格、`⚠️` 标注坑、代码块给命令。
- **先查重**：同一结论已存在就**更新/合并**，不要堆叠重复条目。
- 追加到 `02-使用说明.md` 等已有文档时，融入对应小节的行文/表格，保持整体可读；若确需时间标注可在条目里注明日期。
- 若内容与已有文档冲突(说明旧文档过期) → 一并订正旧处，并在本次说明里点出"订正了 X"。

### 4. 回报

落盘后，用 2-4 行向用户说明：
- 写到了**哪个文件的哪个小节**；
- 记录了**哪几条**(一句话列出)；
- 是否**顺带订正/合并**了旧内容；
- 若有"待核实"项，提示用户确认。

## 注意

- 数据/安全铁律照旧：**绝不**把密钥、token、内网敏感地址明文写进 docs/(它们会进 git)。需要示例时用占位符。
- 只改 docs/(必要时附带订正被本次结论推翻的旧 docs 段落)；**不要**借机改业务代码。
- 与协作文档分工：完结成果归 `CHANGELOG.md`、进行中状态归 `HANDOFF.md`、代码地图归 `ARCHITECTURE.md`——`doc-record` 只管 `docs/`(面向人的知识沉淀)。
